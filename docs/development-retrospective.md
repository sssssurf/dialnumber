# dialnumber 开发回顾

本文对应 **2026 MoonBit 黑客松**「验收标准」中「可解释」一条:可以使用 AI 辅助,但目标、
路径与质量必须由参赛者掌握。按该条的点名要求组织:**关键架构决策**、**AI 工具在开发中的
作用**、**对现有开源工作的引用**。

文中所有数字都是可复核的,复核命令写在每节末尾。

---

## 1. 项目与范围

dialnumber 是一个纯 MoonBit 的电话号码解析、校验与格式化库,建立在 ITU-T E.164 各国编号
计划(national numbering plan)之上。它只做一件事:把人写的一个号码变成结构化的
`PhoneNumber`,按计划判断其结构是否可能,再渲染回标准形态。

范围边界是刻意划窄的:

- **只做号码本身的结构。** 不查号段归属,不做网络或文件 I/O,不解析 JSON。
- **全部对外函数是全函数。** 输入不合法返回 `None` 或 `false`,不抛异常、不 `panic`、不 `abort`。
- **零外部依赖。** `moon.mod` 没有 `deps` 段,只用 `moonbitlang/core`。

规模(实测):

| 指标 | 数值 |
|---|---|
| 源码行数(库,不含 `cmd` 与测试) | 1 067(7 个源文件) |
| 测试行数 | 577(3 个测试文件) |
| 命令行与演示 | 349(2 个包) |
| 覆盖的编号计划 | 51 个地区 |
| 测试用例 | 50 |
| 外部依赖 | 0 |
| 支持编译目标 | native / wasm / wasm-gc |

复核:`moon test`;行数用 `wc -l` 对库根目录的 `*.mbt` 统计(不含 `cmd` 与测试文件)。

## 2. 关键架构决策

### 决策一:数据表与逻辑分离,表只有一份

`region.mbt` 是唯一的事实源:51 行数据,每行给出地区码、英文名、calling code、国际拨出
前缀(idd)、国内长途前缀(national prefix)和一段类型—长度规格(如
`"f=8 m=9 t=5|6|7|8|9|10|11|12"`)。解析、校验、格式化、`tel:` URI 四个模块**都不自带
任何地区知识**,一律通过 `find_region` 查这张表。

为什么不把长度规则写进校验函数?因为同一份长度既被 `is_possible` 用到,也被
`possible_types`、`possible_lengths`、`format_national` 用到。绑进任一处就会产生多份副本,
更新计划时必然漏改。分离之后新增地区只需在表里加一行。

代价:类型—长度规格是一段自定的紧凑字符串,写错不会被编译器发现。这靠黑白盒测试的
多地区向量兜住(US、GB、JP、CN、IT 等)。

### 决策二:国内号码用 `String`,不用整数

`PhoneNumber.national_number` 是字符串,不是 `Int`。原因只有一个,但很硬:意大利**没有
国内长途前缀**,`02 12345678` 的 `0` 是号码本身的一部分,`+39 02 12345678` 去掉 calling code
后必须以 `0212345678` 保留前导零。用整数存会把这个零吃掉,号码当场变错。

`extension` 同理用字符串,因为分机号也可能有前导零。这一取舍在 demo 输出里被显式展示
(`national: 09012345678`),并由测试固定。

### 决策三:校验叫 `is_possible`,不叫 `is_valid`

这是本项目最重要的一条边界,也是与既有库划清关系的地方。

`dialnumber` 只校验**结构**:calling code 在表里,且国内号码长度是该计划用过的长度之一。
它能告诉你 `+81 90-1234-5678` 是一个形状合法的日本移动号,但**不能**告诉你这号线存在、
可达、属于谁。判定后者需要每个计划的前导数字区间与分配记录,本项目不携带。

所以对外**没有** `is_valid`。判据的名字用 `is_possible`,与 libphonenumber 对长度检验
所用的同一个词保持一致,让调用方一眼看出这是长度级检验而非归属级检验。

### 决策四:`possible_types` 返回候选集,不是结论

`possible_types(pn)` 返回该长度**可能**属于的号码类型集合(固话、移动、免费、付费、
共享成本、voip、uan、个人号、寻呼、语音信箱),而不是一个类型。

因为多个类型常常共用一个长度:`+44 7400 123456` 的长度同时落在固话、移动、免费等多个
类型上。若要给出唯一结论,就必需前导数字模式——那正是本项目有意不携带的数据。返回候选集
比返回一个看似确定、实则在缺口处最自信的答案是更诚实的做法。

### 决策五:错误信号用 `Option` / `Bool`,不用异常

`parse(input, region) -> PhoneNumber?`,`is_possible(pn) -> Bool`。`None` 一律表示**输入
形态不对**(calling code 不认识、含非法字符、分机标记后无数字),而不是"这个号码不对"。

为什么不用 `Result` 携带原因?调用方是表单校验与批量清洗,它们只需要一个判断;诊断信息
在批量场景没有位置放,还会诱导调用方去 `unwrap`。本库的取舍是把"为什么"留给调用方自己
按需调 `region_of_number` / `possible_types`。

### 决策六:分机标记的容忍度是被测出来的,不是猜的

分机识别接受 `x`、`#`、`ext.`、`;ext=` 四种写法。这里踩过一个真实的坑:`"+14155550123 ext. 9"`
最初没被正确切出,因为单个标点剥离只处理了标记字符本身,没处理 `ext` 与数字之间那个空格和
句点。修法是先剥标记、再循环剥 `.` / `:` / 空格,并把主号 `trim` 干净。修复后 `ext.` 的
用例被写进测试向量。

另一条边界由此显形:`"+14155550123x"`(有标记、无数字)**不**当分机处理,于是整串不可读、
返回 `None`。测试显式期望这个结果,把"裸标记不算分机"钉死。

### 决策七:不做 locale 数字分组

`format_international` 输出 `+81 9012345678`,而不是 `+81 90-1234-5678`。

要正确插入 `-1234-` 需要各国的前导数字模式,属于决策三划定的缺口之外。一个通用分组器会
**恰好在它看起来最自信的地方出错**,这比让调用方自己分组更糟。所以本库只输出无分组形态,
把显示分组留给调用方。

### 决策八:`cmd/main` 与库共用同一套函数

`cmd/main` 的 9 个子命令(`parse` / `possible` / `format` / `types` / `region` / `info` /
`cc` / `tel` / `list`)只做参数解析与输出排版,逻辑全部调用库里的 `pub fn`。因此 CLI 不存在
"另一份实现",也就不会出现库与 CLI 行为不一致。

### 决策九:文档与代码同源,且由 CI 钉住

`README.mbt.md` 被 `moon.mod` 指定为 `readme`,供 mooncakes.io 渲染;`README.md` 是它的
手同步渲染镜像,供 GitHub 阅读。`docs/reproducible-demo.md` 记录 demo 的完整输出,而
`scripts/check-docs.mjs` 在每次 CI 里**重跑 demo、重跑 README 里记录的每条命令、并从一次
真实的 `moon test` 里读出用例总数**,任何一处与仓库文本不符就失败。文档因此不会静默过期。

### 决策十:测试分黑盒、白盒、健壮性三层

`dialnumber_test.mbt` 只调用 `pub fn`,模拟外部调用方;`dialnumber_wbtest.mbt` 直接测包内
私有辅助函数(`slice`、`split_extension`、`lengths_of` 等);`robustness_test.mbt` 专喂
垃圾、500 位数字、孤立分隔符等,验证"全函数、不 panic"这条承诺。分层让"公开契约"与
"内部实现"各有独立回归网:私有函数可重构,只要黑盒测试不动,契约就没破。

## 3. AI 工具在开发中的作用

项目采用 AI 原生的工作方式,但**职责划分是有意设计的**:AI 负责把已经确定下来的规格翻译
成代码、补测试、补齐文档骨架;作者负责决定架构、划定范围、审阅每一处取舍,并对"号码标准
到底怎么写"负最终责任。

具体而言,AI 参与并产生实质帮助的环节:

- **按计划数据逐条落地。** 把编号计划元数据转成 MoonBit 的类型—长度表,是最耗时的机械
  劳动。从 XML 里抄错一个长度,人眼很难发现。
- **补参考向量。** 测试向量取自各计划公开发布的示例号码(如 NANP 的 `201-555-0123`、
  日本的 `090-1234-5678`、中国的 `131 2345 6789`),而不是自己造输入,避免"用被测代码生成
  自己的期望值"这种循环论证。
- **健壮性测试矩阵。** 用空串、纯空白、全角数字、超长串(500 位)、内嵌空格、孤立分隔符
  等横穿公开函数调用点,验证全函数承诺。穷举由 AI 生成性价比高,人工写容易漏组合。
- **跨环境验证。** 项目在 Windows 上因 moonc 版本过低无法编译,所有真实验证都在 WSL
  Ubuntu-24.04(moonc 0.10.14)里跑 `moon check` / `moon test`。

作者决策并负责的环节:两层架构与表结构、`String` 承载国内号、`is_possible` 的命名与边界、
候选集语义、错误信号选型、分组器的取舍、范围边界,以及本文所述的每一项取舍。

一条边界:**AI 生成的代码必须过 `moon check` 与 `moon test` 才能进入仓库**,没有例外。仓库
的 commit 历史保持线性、可读,每条对应一次真实的功能、测试或文档改动。

## 4. 对现有开源工作的引用

### 数据来源

编号计划表来自 Google 的
[libphonenumber](https://github.com/google/libphonenumber) 元数据
(`PhoneNumberMetadata.xml`,Apache-2.0),它跟踪各计划的官方数据。**本项目只复现其长度
规则,不含前导数字模式**——被省略的那部分正是让 `is_possible` 保持在长度检验这一级的
原因。库代码本身按规格独立编写,未移植或复制任何现有库的代码。

标准依据:ITU-T E.164(国际号码结构)、IETF RFC 3966(`tel:` URI,含 `;ext=` 与
`;phone-context=`)。

### MoonBit 生态中的相邻项目

本库与以下项目是**互补而非重复**关系:

- `moon_zod` / `moonschema` / `jsonschema` —— JSON 与数据结构的 schema 校验,管字段类型和
  email、uuid 之类格式约束,不知道电话编号计划的任何事。
- `moovalid` / `maru` —— 校验组合子与错误累积框架。
- `mooncontract` —— OpenAPI 接口契约校验。
- `moonmrz` —— 面向护照/签证 ICAO 9303 机读区。

在 mooncakes.io 上以 phone、e164、msisdn、libphonenumber、telephone、phone number 等关键词
检索,目前无任何相关模块命中。

## 5. 已知限制

明确写出来,避免被当成缺陷重复报告:

1. **只校验结构,不校验分配。** `is_possible` 通过不代表号码真实存在或可达。本库不查号段
   数据库,这是有意边界(见决策三)。
2. **无 locale 数字分组。** `format_international` / `format_national` 输出无分隔符,需要
   前导数字模式才能正确分组,属缺口之外(见决策七)。
3. **地区表是静态的 51 项。** 新增地区或长度调整需要更新 `region.mbt` 的表,不是自动抓取。
4. **`native` 目标需要系统 C 编译器。** 纯 MoonBit 代码可编译到 native,但链接阶段依赖
   cl/clang/gcc;CI 的 `build-matrix` 在 ubuntu-latest 上提供 gcc,该目标在 CI 中被真实验证。
   本地若无 C 编译器,`moon build --target native` 会失败并提示找不到 C 编译器,这不是代码缺陷。

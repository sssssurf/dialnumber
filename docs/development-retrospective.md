# dialnumber 开发回顾

本文对应 **2026 MoonBit 黑客松**「验收标准」中「可解释」一条:可以使用 AI 辅助,但目标、
路径与质量必须由参赛者掌握。按该条的点名要求组织:**关键架构决策**、**AI 工具在开发中的
作用**、**对现有开源工作的引用**。

文中所有数字都是可复核的,复核命令写在每节末尾。

---

## 1. 项目与范围

dialnumber 是一个纯 MoonBit 的电话号码解析、校验与格式化库,建立在 ITU-T E.164 各国编号
计划(national numbering plan)之上。它把人写的一个号码变成结构化的 `PhoneNumber`,用计划
自己公布的规则判断它,再渲染回标准形态。

范围边界是刻意划定的:

- **规则来自计划本身,不来自猜测。** 每个地区携带该计划各号码类型的规则(前导数字模式),
  由库内的模式引擎解释;库不内置任何"经验性"判断。
- **全部对外函数是全函数。** 输入不合法返回 `None` 或 `false`,不抛异常、不 `panic`、不 `abort`。
- **零外部依赖。** `moon.mod` 没有 `deps` 段,只用 `moonbitlang/core`,没有正则库。
- **数据可复现。** 号码表由脚本从上游元数据生成,并记录上游文件的 SHA-256;手改生成文件会
  被 CI 拒绝。

规模(实测):

| 指标 | 数值 |
|---|---|
| 手写库源码(9 个文件,不含生成的表) | 2 787 行 |
| 生成的号码表 `plan_data.mbt` | 3 843 行 / 232 KB |
| 覆盖的编号计划 | 245 个地区 |
| 逐类型规则(模式) | 1 132 条 |
| 号码格式规则(分组) | 740 条 |
| 上游公布的示例号码(全部成为用例) | 1 132 个 |
| NANP 区号覆盖 | 25 个地区 |
| 对外函数 | 45 个 |
| 测试块 | 339 个(另有 2 264 条差异断言与 1 900 次随机用例) |
| 手写测试源码 | 1 356 行(8 个文件) |
| 命令行与演示 | 488 行(2 个包) |
| 基准测试 | 77 行(`moon bench benchmarks`) |
| 外部依赖 | 0 |
| 支持编译目标 | native / wasm / wasm-gc |

复核:`moon test`;行数用 `wc -l` 对库根目录 `*.mbt` 统计(不含 `cmd` 与测试文件);
规则数与示例数见 `data/numbering-plans.json` 的 `meta` 段。

## 2. 关键架构决策

### 决策一:数据是生成的,逻辑只解释数据

`plan_data.mbt` 是唯一的事实源,由 `scripts/gen-metadata.mjs` 从
`data/numbering-plans.json` 生成;JSON 又由 `scripts/update-metadata.mjs` 从 libphonenumber
的 `PhoneNumberMetadata.xml` 抽取。解析、校验、类型判定、格式化、`tel:` URI 五个模块
**都不自带地区知识**,一律通过 `find_region` 查表。

为什么不让表由人手写?0.2.0 的表是 51 行手写数据,一次刷新就要人肉核对每个长度;而 0.3.0
有 245 个地区、1 132 条规则,手写既不现实也无法复核。生成之后,数据更新是"重跑脚本 + 看
diff",而 diff 是可读的 JSON。

代价:仓库里多了生成产物。用三条 `--check` 的 CI 步骤把它按住——生成器在 check 模式下若
发现产物与源不一致就失败,因此手改生成文件或改了 JSON 忘了重生成都会在 CI 里暴露。

### 决策二:国内号码用 `String`,不用整数

`PhoneNumber.national_number` 是字符串,不是 `Int`。原因只有一个,但很硬:意大利**没有
国内长途前缀**,`02 12345678` 的 `0` 是号码本身的一部分,`+39 02 12345678` 去掉 calling code
后必须以 `0212345678` 保留前导零。用整数存会把这个零吃掉,号码当场变错。

`extension` 同理用字符串,因为分机号也可能有前导零。这一取舍在 demo 输出里被显式展示
(`national: 09012345678`),并由测试固定。

### 决策三:自己写模式引擎,而不是引入正则

计划规则是正则表达式(如 `(?:2(?:04|[23]6|[48]9)|3(?:06|43|54))\d{7}`),但:

- MoonBit 核心库没有正则实现,引入外部正则库会破坏"零依赖";
- 即使有,通用正则的回溯在恶意输入上会指数爆炸,而校验函数会在表单与批量清洗里被直接喂
  用户输入。

因此 `pattern.mbt` 实现了一个**只吃编号计划文法**的引擎:递归下降解析成语法树,编译成
Thompson NFA,再用状态集合模拟匹配。文法只包含计划数据里真实出现的算子——字面量、`\d`、
字符类与区间、非捕获组、`|`、`?`、`*`、`+`、`{n}`、`{n,}`、`{n,m}`。这带来三条可测的性质:

- **复杂度是 O(模式长度 × 输入长度)**,没有回溯,不存在灾难性回溯;
- **全函数**:解析不了的规则匹配任何输入都为 false,坏数据不会变成误判;
- **可自证**:`pattern_well_formed` 把"这条规则在文法内"变成可断言的事实,数据管线在抽取
  阶段就对每条规则做同一检查。

### 决策四:两级校验,名字分别是 `is_possible` 和 `is_valid`

两个问题不同,库用两个函数回答,并且不合并:

- `is_possible`:calling code 认识,且国内号码长度是计划用过的长度之一(对 `+1` 还叠加
  NANP 形状规则)。这是 libphonenumber 的 "possible"。
- `is_valid`:国内号码匹配计划公布的某条类型规则。这是 libphonenumber 的 "valid"。

0.2.0 只有前者,因此只能诚实地说"结构上可能";0.3.0 携带了规则,于是可以给出后者。两者
在 demo 里被并排展示:`+1 555-555-0123` 形状合法(possible 为是),但 555 不是已分配区号
(valid 为否);`+81 90-1234-567` 少一位,同样 possible 为是、valid 为否。

### 决策五:`number_type` 用 libphonenumber 的优先级,并保留 `FixedLineOrMobile`

`number_type` 不是"按长度猜",而是按规则判定,顺序与 libphonenumber 一致:特殊号段
(免费、付费、共享成本、voip、个人号、寻呼、uan、语音信箱)先于地理号段;同时匹配固话与
移动时返回共享的 `FixedLineOrMobile`。`NumberType` 因此从 10 个取值变成 11 个。

`possible_types` 仍然保留,语义明确为**长度级候选集**;两者在文档与 CLI 里都并排出现
(`length candidates: ...` / `pattern verdict: ...`),避免调用方把它们混为一谈。

### 决策六:错误信号用 `Option` / `Bool`,不用异常

`parse(input, region) -> PhoneNumber?`,`is_valid(pn) -> Bool`。`None` 一律表示**输入形态
不对**(calling code 不认识、含非法字符、分机标记后无数字),而不是"这个号码不对"。

为什么不用 `Result` 携带原因?调用方是表单校验与批量清洗,它们只需要一个判断;诊断信息在
批量场景没有位置放,还会诱导调用方去 `unwrap`。本库的取舍是把"为什么"留给调用方按需调
`region_of_number` / `number_type` / `plan_pattern`。

### 决策七:分组来自计划的格式规则,不是通用算法

`format_international` 输出 `+81 90-1234-5678`,而不是 `+81 9012345678`;`format_national`
输出 `(201) 555-0123`、`020 7946 0958`、`8 (495) 123-45-67`。

这些分组不是猜的:表里 740 条格式规则,每条给出"数字分组形状 + 组间文本 + 选择用的前导数字
+ 国际变体 + 国内前缀规则"。渲染时按前导数字选第一条匹配形状的规则,再做 `$1..$9` 代入;
国内前缀规则里 `$NP` 展开为长途前缀、`$FG` 只覆盖第一组(所以澳洲的 `($NP$FG)` 得到
`(02) 1234 5678`,巴西的 `($FG)` 得到 `(11) 98765-4321`)。没有规则匹配的形状退回无分组形态。

不做一个通用分组器,是因为通用分组器在跨国场景里必然出错;分组规则本身是公开数据,照做即可。
这条取舍有一个可判定的验证方式:每个固话/手机示例的国内形态必须能被同一地区重新解析回原号码
——生成测试对全部示例断言这一点(少数会改写号码的计划除外,见已知限制)。

### 决策八:解析长途前缀用计划公布的模式

国内号码的前缀不总是单个字符:白俄罗斯可拨 `0`、`8`、`80`,日本有 `0037` 一类国际前拨码。
表里除 `national_prefix` 外还保留上游的 `nationalPrefixForParsing`;当它在引擎文法内时,
用它找出能匹配的最长前缀并剥掉,否则退回朴素的字面前缀。这条让"格式化 → 再解析"的往返在
更多地区成立。

### 决策九:共享 calling code 用规则消歧,主地区赢平局

一个 calling code 可以被多个地区共用(245 个地区里有 51 个地区与别人共享代码,`+1` 更是
25 个)。`region_of_number` 的判定顺序是:

1. 先用各地区的类型规则匹配,主地区(`mainCountryForCode`)优先;
2. 没有规则匹配时,退回到"长度被某个地区承认"的地区,保证 possible 的号码仍有归属;
3. 都不满足则 `None`。

这与 0.2.0 的"美/加二元判断"不同:0.2.0 的加拿大 NPA 集合是手写常量,0.3.0 换成各地区
自己公布的模式,于是波多黎各(787/939)、牙买加(876/658)、特立尼达(868)、巴哈马(242)
等都能各自解析,而不是被算进美国。

### 决策十:测试由数据生成,并另加一层独立参照

手写测试难以覆盖 1 132 条规则。0.3.0 的测试体系分四层:

- **数据生成的黑盒测试**:每个地区一个块,断言该地区每个类型的示例号码被本地区规则接受、
  解析到数据规定的地点、并给出合理类型。示例号码是上游公布的,不是自己造的,避免"用被测
  代码生成自己的期望值"这种循环论证。
- **差异语料**:每条规则取一个示例和一个变异反例,期望值由一个**独立的 JavaScript 正则实现**
  算出,再由 MoonBit 引擎复现,共 2 264 条断言。这是跨实现互证,不是自证。
- **手写单元测试**:文法、算子语义、拒绝集、长输入下的线性行为、`tel:` 文法与 RFC 3966
  示例。
- **健壮性测试**:空串、纯空白、全角字符、500 位数字、孤立分隔符横穿所有公开函数。

### 决策十一:文档与代码同源,且由 CI 钉住

`README.mbt.md` 被 `moon.mod` 指定为 `readme`,供 mooncakes.io 渲染;`README.md` 由
`scripts/sync-readme.mjs` 生成,GitHub 上读的就是它。`docs/reproducible-demo.md` 记录 demo
的完整输出,而 `scripts/check-docs.mjs` 在每次 CI 里**重跑 demo、重跑 README 里记录的每条
命令、并从一次真实的 `moon test` 里读出用例总数**,任何一处与仓库文本不符就失败。

### 决策十二:`tel:` URI 把上下文当数据,不当前缀

RFC 3966 的本地号必须带 `;phone-context=`,上下文有两种:数字前缀(`+1-919`)或域名
(`example.com`)。0.1.0 把上下文 `digits_of` 后拼进号码,域名上下文直接返回 `None`——前者
丢失了"上下文是什么",后者丢掉了"URI 本身合法"这个事实。

现行实现把解析与消解分开:

- `TelUri` 保留 `global_number` / `local_number` / `phone_context` / `extension` / `isub`
  五个字段,上下文永不并入号码;
- `parse_tel_uri_full` 按文法接受两类上下文;`resolve_tel_uri` 只对数字上下文求解;
- `parse_tel_uri_full` 与 `to_tel_uri_full` 互为逆运算,由往返测试钉住;
- 文法上拒绝而非静默丢弃:未知/重复/空参数、空值、`ext` 与 `isub` 同时出现、全局号带上下文、
  RFC 3966 §5.1.1 明确不允许的内部空格;
- `isub` 按 `uric` 校验:每个 `%` 必须带完整的两位十六进制,十六进制统一大写,因此规范化
  后仍能往返。0.2.0 只检查了字符集,`%ZZ` 一类会被放过——这是 0.3.0 修掉的标准符合性缺口。

### 决策十三:数据管线自带出处与不变量

`data/numbering-plans.json` 的 `meta` 段记录上游 URL、许可证、抓取日期、上游文件的 SHA-256、
地区数与规则数。生成表时把这些信息写进文件头,测试再断言"表里的地区数/规则数与元数据一致"
"每条规则都在引擎文法内""每个地区都有名字且可查""`+1` 空间恰好 25 个地区"。数据管线的
承诺因此是可执行的,不是注释里的声明。

---

### 决策十四:规则编译一次,匹配只走活状态

0.5.0 之前,每次校验都会重新解析并编译规则:一条 1 400 字符的美国固话规则要几十微秒,
`is_valid` 在 +1 号码上要 2.45 毫秒。两处改动把它降到 48 微秒:

- **编译结果记忆在表里。** 类型规则、计划总规则、长途前缀规则各有一个 `Ref` 缓存,首次使用
  时编译,之后复用;
- **匹配只遍历活状态。** NFA 模拟不再逐字符扫描整个程序,而是维护"当前存活状态"列表,并用
  代数戳标记已访问状态。长轮换规则在第一个数字之后只剩少数分支存活,代价随活分支走而不是
  随规则长度走。

基准测试进了仓库(`moon bench benchmarks`),数字写在 README 的性能一节:性能回归会以数字
的形式出现,而不是靠感觉。

## 3. AI 工具在开发中的作用

项目采用 AI 原生的工作方式,但**职责划分是有意设计的**:AI 负责把已经确定下来的规格翻译
成代码、补测试、补齐文档骨架;作者负责决定架构、划定范围、审阅每一处取舍,并对"号码标准
到底怎么写"负最终责任。

具体而言,AI 参与并产生实质帮助的环节:

- **按计划数据逐条落地。** 把 245 个地区、1 132 条规则从 XML 转成 MoonBit 表,是最耗时的
  机械劳动。从 XML 里抄错一个字符,人眼几乎不可能发现。
- **数据管线。** 抽取、展开长度区间、校验文法、生成表与测试,都是可重复的脚本,而不是一次性
  手工整理。
- **交叉验证语料。** 用另一种实现(JavaScript 正则)算出期望值,让两种实现对同一批规则互相
  印证,这是人写测试很难铺开的规模。
- **健壮性测试矩阵。** 用空串、纯空白、全角数字、超长串(500 位)、内嵌空格、孤立分隔符
  横穿公开函数调用点,验证全函数承诺。
- **跨环境验证。** 项目在 Windows 上因 moonc 版本过低无法编译,所有真实验证都在 WSL
  Ubuntu-24.04(moonc 0.10.14)里跑 `moon check` / `moon test` / `moon run cmd/demo`。

作者决策并负责的环节:两级校验的划分与命名、模式引擎的选型(自写 NFA 而非引入正则)、
数据管线的分层与 check 模式、生成测试与差异语料的策略、错误信号选型、分组器的取舍、范围
边界,以及本文所述的每一项取舍。

一条边界:**AI 生成的代码必须过 `moon check` 与 `moon test` 才能进入仓库**,没有例外。仓库
的 commit 历史保持线性、可读,每条对应一次真实的功能、测试或文档改动。

## 4. 对现有开源工作的引用

### 数据来源

编号计划数据来自 Google 的
[libphonenumber](https://github.com/google/libphonenumber) 元数据
(`PhoneNumberMetadata.xml`,Apache-2.0)。0.3.0 复现的是**完整的逐类型规则**,不再是只取
长度:抽取脚本把 245 个地理 territory 的 `generalDesc` 与 10 个号码类型的
`nationalNumberPattern`、`possibleLengths`、`exampleNumber` 一并取出,去掉排版空白后存入
JSON。九个非地理 territory(`001` 行:`+800` 国际免费电话等)描述的是网络而非地区,表以
地区为键,因此显式跳过,并由脚本打印跳过数量。

地区英文名由生成器通过 Node 的 `Intl.DisplayNames`(CLDR)取得,随数据一起写入表。

标准依据:ITU-T E.164(国际号码结构)、IETF RFC 3966(`tel:` URI 与 `;ext=` /
`;phone-context=` / `;isub=` 参数)、RFC 3986(URI 字符集与百分号转义)。NANP 的形状规则
(NPA/NXX 首位 2–9、N11 非区号)来自 NANP 的公开编号结构。

库代码按规格独立编写,未移植或复制任何现有库的实现。

### MoonBit 生态中的相邻项目

本库与以下项目是**互补而非重复**关系:

- `moon_zod` / `moonschema` / `jsonschema` —— JSON 与数据结构的 schema 校验,管字段类型和
  email、uuid 之类格式约束,不知道电话编号计划的任何事。
- `moovalid` / `maru` —— 校验组合子与错误累积框架。
- `mooncontract` —— OpenAPI 接口契约校验。
- `moonmrz` —— 面向护照/签证 ICAO 9303 机读区。

在 mooncakes.io 上以 phone、e164、msisdn、libphonenumber、telephone 等关键词检索,目前无
任何相关模块命中。

## 5. 已知限制

明确写出来,避免被当成缺陷重复报告:

1. **valid 到规则为止,不到线路。** `is_valid` 表示号码落在计划公布的某个类型规则里,不表示
   这号线存在、可达或属于谁。后者需要运营商级分配记录,本库不携带。
2. **非地理 calling code 不在表内。** `+800`、`+870`、`+878` 一类国际网络没有地区可归属,
   表以地区为键,因此不收录;它们会返回 `None`,而不是被错误地归到某个国家。
3. **`tel:` 域名上下文不求解。** 它能被完整解析、规范化与往返,但无法在没有该域权威数据的
   情况下变成 E.164 号码。
4. **少数计划的长途拨号无法反向还原。** 阿根廷手机在国内写作 `011 15-…`、国际上带 `9`,
   白俄罗斯会丢掉一位;这类"解析时改写号码"的机制(`nationalPrefixForParsing` 配合 transform
   规则)没有实现,生成式往返测试对这类计划显式跳过,而不是假装通过。
5. **号码表是有日期的快照。** 表由上游元数据生成,`data/numbering-plans.json` 记录抓取日期
   与 SHA-256;重新抓取是显式操作,不是在运行时联网更新。
6. **`native` 目标需要系统 C 编译器。** 纯 MoonBit 代码可编译到 native,但链接阶段依赖
   cl/clang/gcc;CI 的 `build-matrix` 在 ubuntu-latest 上提供 gcc,该目标在 CI 中被真实验证。
